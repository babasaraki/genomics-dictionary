Containerisation

Bioinformatics and statistics Published

Definition

Containerisation packages a piece of software together with the libraries and settings it needs, so that it runs the same way on any machine with a compatible container runtime. In bioinformatics it solves a persistent problem: analyses depend on long chains of tools and libraries whose versions differ between computers, and those differences quietly change results.

Technical explanation

A container image is a layered, read-only filesystem built from a recipe that records every installation step. The running container shares the host kernel, which makes it far lighter than a virtual machine while still isolating the software stack. Images are addressed by a tag and, more reliably, by a content digest, and are pulled from registries. Runtimes designed for shared research computing avoid requiring administrative privileges and convert images to a single-file format convenient on cluster filesystems. Workflow managers can attach a specific image to each step, so a pipeline carries its own software. Containers are complementary to package environment managers, which pin versions within a language ecosystem rather than packaging the whole stack. Two caveats matter. An image built from a recipe that installs the latest version of each dependency is not reproducible, because rebuilding it later yields different software; pinning versions and archiving the built image are what provide the guarantee. And a container isolates software, not data: reference genomes, annotation files and databases are usually mounted from outside and must be versioned separately.

Practical example

A training course distributes a single container image holding the aligner, variant caller and R packages used in the practicals. Participants on Linux, macOS and institutional clusters all obtain identical outputs from the exercise dataset, so teaching time is spent on interpretation rather than on resolving installation failures.

Common misunderstanding

Containers are often assumed to freeze an analysis completely. They freeze the software, not the inputs. A pipeline running in a fixed image will still produce different results if it is pointed at a new reference build, an updated annotation release or a refreshed variant database, because those resources usually live outside the image.
