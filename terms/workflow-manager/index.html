Workflow manager

Bioinformatics and statistics Published

Definition

A workflow manager is software that describes an analysis as a set of steps with declared inputs and outputs, then runs those steps in the right order, in parallel where possible, on a laptop, a cluster or in the cloud. It keeps track of what has already completed, so an interrupted run can resume rather than start again from the beginning.

Technical explanation

In a workflow language, each process declares the files it consumes and produces and the command it runs; the manager infers the dependency graph from those declarations rather than from the order in which they were written. This brings several practical benefits: steps that do not depend on one another are executed concurrently, the same description runs on different executors because scheduler details are kept in configuration rather than in the script, failed tasks can be retried with more memory, and completed tasks are cached so that re-running after a change recomputes only what is affected. Combining a workflow description with pinned software environments, usually containers, and with a version-controlled repository gives an analysis that another group can execute on their own data. The costs are a steeper learning curve than a shell script, an extra layer to debug when a task fails inside a container on a remote node, and the temptation to treat a community pipeline as a black box. A workflow guarantees that the same steps run; it does not guarantee that those steps suit the data.

Practical example

A genomic surveillance programme processes sequencing runs weekly. The workflow is written once with per-sample steps for quality control, assembly, typing and resistance screening. When one sample fails on memory, only that task is retried at a larger allocation, and the rest of the batch, already cached, is not recomputed.

Common misunderstanding

Using a workflow manager is sometimes equated with having a reproducible analysis. It makes the orchestration repeatable, but reproducibility also requires pinned tool versions, recorded reference and annotation builds, archived parameters and accessible input data. A workflow that calls whichever version of a tool happens to be installed will not reproduce across machines.
